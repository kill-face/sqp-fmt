sqlparser-rs Field Guide

How apache/datafusion-sqlparser-rs turns SQL text into a syntax tree and back, how the formatter tsqlfmt uses that tree to lay out T-SQL, and a change-by-change review of the local fork both depend on.

Upstream pinned at 2ff068b3 (main, 19 Nov 2026) Fork bookmark tsql, 55 changes Read-only review: nothing in either repo was changed

0How to use this page

The page has four parts. The primer defines the vocabulary of lexing and parsing with tiny examples, and the Rust idioms section explains the language features the parser leans on. The architecture section walks the crate from SQL text to Vec<Statement> and back, ending with the recipe for adding syntax. tsqlfmt shows how the formatter consumes the parser and where its design sits among other formatters. The fork review explains and judges every change on the tsql bookmark.

Links into upstream code are pinned to commit 2ff068b30954e1d67889550fae8539640422c61a, and their line numbers were checked against that commit. The fork is not pushed anywhere, so fork changes are identified by their jj change id (for example umlurknv), the local path ~/code/personal/datafusion-sqlparser-rs, and short diff excerpts. To read one in full: jj show umlurknv.

All SQL on this page is invented for illustration.

1Primer: the vocabulary

Each term is defined where it is first needed, with the smallest example that shows it. Later sections use these words without re-defining them.

Lexer, tokenizer

The first pass. It reads characters and groups them into tokens, without knowing anything about the structure of statements. In sqlparser-rs this is Tokenizer; the two words mean the same thing.

price*1.2   →   Word(price)  Mul  Number(1.2)
Token, lexeme

A token is a classified chunk of input: a word, a number, a string literal, a punctuation mark. The lexeme is the exact source text the token came from. Two lexemes can produce the same token kind: <> and != both become Token::Neq. A parser that only keeps tokens has lost which one you wrote; a formatter cannot afford that.

Keyword vs identifier

A keyword is a word the language reserves or gives meaning to (SELECT, FROM). An identifier names something you created (a table, a column). SQL blurs the line: many keywords are non-reserved and can still be used as names. sqlparser-rs lexes every bare word as Token::Word and records whether it matches a known keyword; the parser decides from context. In SELECT name FROM t, name is lexed as Word { keyword: NAME } but parsed as a column. Quoting removes the keyword match: [select] or "select" is always an identifier (keyword_lookup).

Trivia

Input that does not change meaning: spaces, newlines, tabs and comments. The term comes from Roslyn. sqlparser-rs keeps trivia in the token stream as Token::Whitespace(..) but the parser skips over it, so the tree has no trivia in it. A formatter must put every comment back, so where trivia lives is a central design question (see tsqlfmt).

Grammar

The rules that say which token sequences form valid statements, written as productions: a name on the left, what it may consist of on the right. A grammar describes syntax (shape), not semantics (whether the table exists). sqlparser-rs is explicitly a syntax-only parser.

BNF, EBNF, syntax diagrams

BNF (Backus–Naur form) writes productions as <select> ::= SELECT <item-list> FROM <table>. EBNF adds shorthand for optional parts and repetition. Vendors document SQL in their own EBNF-like notation. Microsoft's Transact-SQL syntax conventions use [ x ] for optional, { a | b } for "pick one", [ ,...n ] for "repeat, comma-separated" and <label> ::= for a named sub-rule. When this page asks whether a change "matches the documented grammar", it means these pages.

CREATE [ UNIQUE ] [ CLUSTERED | NONCLUSTERED ] INDEX index_name
    ON <object> ( column [ ASC | DESC ] [ ,...n ] )
Recursive descent

A way to write a parser by hand: one function per grammar rule, each calling the functions for its parts. parse_query calls parse_select, which calls parse_expr for each projection item, which may call parse_query again for a subquery. The call stack mirrors the tree being built. sqlparser-rs is a hand-written recursive-descent parser; there is no grammar file or parser generator.

Lookahead, backtracking

Lookahead is peeking at upcoming tokens to decide which rule applies without consuming them. BEGIN TRANSACTION and BEGIN ... END start the same way; the parser looks at the next token to choose. Backtracking is trying a rule, and if it fails, rewinding to where you started and trying another. sqlparser-rs does this with maybe_parse, which saves the token index, runs a closure, and restores the index on error. Backtracking is convenient but can turn into exponential work; upstream caches failed prefix parses for that reason (parse_prefix).

Precedence, associativity

Precedence says which operator binds tighter: a + b * c is a + (b * c) because * outranks +. Associativity settles ties between equal operators: a - b - c is (a - b) - c, which is left-associative. Upstream's precedence table is Dialect::prec_value: * is 40, + 30, comparison 20, AND 10, OR 5.

Pratt parsing

A compact way to parse expressions with precedence, from Vaughan Pratt's 1973 paper "Top down operator precedence". Parse one operand (the prefix), then loop: look at the next operator's precedence; if it binds tighter than what the caller allows, consume it and parse its right side with that precedence as the new floor (the infix). Also called precedence climbing. matklad's tutorial is the best short introduction. Section 3.4 steps through it.

AST vs CST

An abstract syntax tree keeps meaning and drops spelling: Expr::BinaryOp { left, op: Plus, right } does not record the parentheses, spaces, comments or keyword case you typed. A concrete syntax tree keeps every token. A lossless CST also keeps the trivia, so printing it gives back the input byte for byte. Roslyn, rust-analyzer (rowan) and Biome use lossless trees. sqlparser-rs builds an AST.

Source span

The start and end position of a piece of syntax in the input. sqlparser-rs uses 1-based (line, column) pairs: Location and Span. Every token has an exact span. AST nodes compute theirs on demand through the Spanned trait, and some are incomplete (section 3.7). In practice the end column is one past the last character: SELECT at the start of a line spans columns 1 to 7.

Dialect

A variant of SQL: T-SQL (SQL Server), PostgreSQL, MySQL, Snowflake and so on. In sqlparser-rs a dialect is a value implementing the Dialect trait, consulted by both tokenizer and parser (MsSqlDialect lets identifiers start with @ and #, for example). GenericDialect tries to accept the union of all of them.

Visitor

Code that walks a tree and gets a callback at each node of interest, without writing the traversal by hand. sqlparser-rs generates the traversal with a derive macro and lets you implement Visitor callbacks such as pre_visit_expr.

Unparsing, round-tripping

Unparsing turns a tree back into text. A round trip is parse, then unparse, then compare. sqlparser-rs unparses through Display, producing canonical text: keywords upper-cased, single spaces, optional AS inserted. Its tests require that canonical text re-parses to the same tree (verified_stmt). That is not the same as reproducing your input, which is why a formatter cannot simply print the AST.

select a  as x from t   →  SELECT a AS x FROM t

2The Rust idioms the parser relies on

You can read most of the parser knowing these eight patterns. Each example is a trimmed version of real upstream code.

Enums that carry data

A Rust enum is a sum type: a value is exactly one of the variants, and each variant can hold its own fields. This is the natural shape of a syntax tree, where an expression is either an identifier or a binary operation or a function call. Code that consumes it uses match, and the compiler rejects a match that forgets a variant. That is why adding a variant to Expr or Statement forces edits in Display, Spanned and the visitor.

pub enum Expr {
    Identifier(Ident),                                   // tuple variant
    BinaryOp { left: Box<Expr>, op: BinaryOperator, right: Box<Expr> },  // struct variant
    Nested(Box<Expr>),
    // ... about 90 more
}

Source: src/ast/mod.rs L956.

Box for recursive types

A Rust value must have a size known at compile time. Expr contains Exprs, so storing them inline would make the type infinitely large. Box<Expr> is a pointer to a heap allocation, so it has a fixed size. A second reason for boxing: an enum is as large as its largest variant, so one big variant makes every Expr big. Several fork changes box fields to keep size_of::<Expr>() flat; that is a real upstream concern, not a micro-optimisation.

Result and ?

Fallible functions return Result<T, ParserError>: Ok(value) or Err(error). The ? operator unwraps an Ok or returns the Err to the caller immediately. A parse function reads like a list of expectations, and the first one that fails ends the whole parse with a message such as Expected: FROM, found: WHERE at Line: 1, Column: 10.

pub fn parse_savepoint(&mut self) -> Result<Statement, ParserError> {
    let name = self.parse_identifier()?;   // on Err, return it now
    Ok(Statement::Savepoint { name })
}

Source: parse_savepoint. Errors are the three-variant ParserError.

Peekable and index-based lookahead

The two passes look ahead differently. The tokenizer walks characters through Peekable<Chars> (State), an iterator adapter with a .peek() that shows the next character without consuming it: enough to tell - from --. The parser instead holds the whole Vec<TokenWithSpan> and an integer index. Peeking any distance is cheap (peek_nth_token), and backtracking is just restoring the integer. Whitespace tokens stay in the vector; the peek and advance functions skip them.

Trait default methods: the Dialect trait

A trait method can have a default body. Dialect has about two hundred methods, almost all with defaults, so a dialect overrides only where it differs. Most are boolean capability hooks named supports_*; a few are override hooks that may take over parsing and return None to fall back (parse_prefix, parse_infix, get_next_precedence, parse_statement).

// dialect/mod.rs: the default
fn supports_column_definition_trailing_commas(&self) -> bool { false }
// dialect/mssql.rs: an override
fn supports_create_proc_syntax(&self) -> bool { true }

The older alternative is the dialect_of!(self is MsSqlDialect | GenericDialect) macro, a runtime type check. Upstream's guidance prefers a trait method: a user-defined dialect can opt in, and the difference is documented on the trait (doc comment, AGENTS.md). This distinction drives several verdicts in the fork review.

Derive and procedural macros

#[derive(Debug, Clone, PartialEq)] asks the compiler to generate trait implementations from the type's shape. A procedural macro is a Rust function that runs at compile time and writes code; custom derives are one kind. The separate crate sqlparser_derive provides #[derive(Visit, VisitMut)], which generates a walk over every field of every AST type. The #[visit(with = "visit_expr")] attribute marks where the generated walk should call your pre_visit_expr / post_visit_expr hooks (derive/src/visit.rs).

cfg_attr feature gates

Cargo features are compile-time switches. #[cfg_attr(feature = "visitor", derive(Visit, VisitMut))] means "apply this derive only when the visitor feature is on", so users who do not walk trees do not compile the walker. The crate's features are std, recursive-protection (default), serde, visitor and derive-dialect (Cargo.toml). tsqlfmt enables visitor.

#[derive(Debug, Clone, PartialEq, PartialOrd, Eq, Ord, Hash)]
#[cfg_attr(feature = "serde", derive(Serialize, Deserialize))]
#[cfg_attr(feature = "visitor", derive(Visit, VisitMut), visit(with = "visit_expr"))]
pub enum Expr { ... }

Display as the unparser

impl fmt::Display for T defines what format!("{}", t) prints. Every AST type implements it to print SQL, so statement.to_string() is the unparser. With the alternate flag, format!("{:#}", stmt), some nodes print across indented lines (crate docs, indented_list). Display output is canonical, so it is a test oracle, not a formatter.

// ast/mod.rs, inside impl fmt::Display for Expr
Expr::BinaryOp { left, op, right } => write!(f, "{left} {op} {right}"),
Expr::Nested(ast) => write!(f, "({ast})"),

Source: L1868, L2115.

3sqlparser-rs architecture

The crate is a library with no runtime dependencies beyond log (and optional serde and recursive). It has three main parts, the tokenizer, the parser and the AST, plus the dialects they both consult. Two design rules from the README shape everything else. The parser is syntax only: CREATE TABLE t (x int, x int) parses fine. And it round-trips: printing the AST and parsing it again gives the same AST, "with comments removed, normalized whitespace and keyword capitalization" (README).

3.1Crate layout

Also in src/: test_utils.rs (the TestedDialects harness used by every test file) and display_utils.rs (indentation helpers for {:#} printing). Tests live in tests/sqlparser_<dialect>.rs, with cross-dialect cases in tests/sqlparser_common.rs.

3.2Data flow: text to tree and back

The usual entry point is Parser::parse_sql(&dialect, sql), which is shorthand for Parser::new(&dialect).try_with_sql(sql)?.parse_statements(). To control the parse, use the builder: with_options, and either try_with_sql (tokenize for me) or with_tokens_with_locations (here are tokens I already have). parse_sql_with_comments returns the comments as well.

3.3The tokenizer

Tokenizer holds the dialect, the input and a few flags (whether to unescape string literals, whether to keep their original text). Its main loop, tokenize_with_location_into_buf_with_mapper, calls next_token until the input runs out. Each call looks at the next character and dispatches: a space becomes Whitespace::Space, a letter starts a word, a quote starts a string, - followed by - starts a line comment. The span is computed in one place, from the cursor position before and after the token (L1059).

The types

  • enum Token: about 90 variants. Word(Word) for keywords and identifiers, Number(String, bool), several string-literal kinds, every operator (Mul, Gt, DoubleColon), and Whitespace(Whitespace).
  • struct Word: the text as written, its quote_style ([, ", ` or none) and its keyword, or Keyword::NoKeyword.
  • enum Whitespace: Space, Newline, Tab, SingleLineComment { comment, prefix }, MultiLineComment(String).
  • TokenWithSpan = Token + Span = two Locations, each a 1-based line and column.

Things that surprise people

  • Locations are line and column, not byte offsets. To slice the source you convert; tsqlfmt does this for every token.
  • The doc comment calls the end "inclusive", but tokens end one column past their last character.
  • Location { line: 0, column: 0 } means "unknown". It is how an empty span is spelled.
  • The dialect is consulted while lexing: in T-SQL, @x and #tmp are single words (is_identifier_start), and [a b] is a quoted identifier.
  • A keyword lookup is a binary search of a sorted array generated by define_keywords!.

3.4The parser

struct Parser holds the full token vector, an index into it, the dialect, the options, a recursion counter and two memo tables. Everything is a method on &mut Parser. The vocabulary for moving through tokens is small:

Statements: one big match

parse_statements loops: skip any semicolons, stop at EOF, call parse_statement, then require a delimiter before the next one unless require_semicolon_stmt_delimiter is off. parse_statement first offers the dialect a chance to take over (Dialect::parse_statement; T-SQL uses this for BEGIN … END, IF and CREATE TRIGGER, see mssql.rs). Otherwise it reads one token and matches on its keyword: SELECT | WITH | VALUES | FROM rewind and call parse_query (L670); CREATE goes to parse_create, which matches again on what follows; and so on for about a hundred statement kinds.

Queries: parse_query and parse_select

parse_query parses an optional WITH list, then the body with parse_query_body, then the trailing clauses (ORDER BY, LIMIT, FETCH, FOR XML, locks). The body is itself parsed with precedence climbing, because UNION, EXCEPT and INTERSECT are binary operators over query bodies. Each operand is a (subquery), a VALUES list or a parse_select, which reads the clauses of one SELECT in their fixed order: TOP, DISTINCT, the projection, INTO, FROM (parse_table_and_joins → parse_table_factor), WHERE (L16562), GROUP BY, HAVING, WINDOW, QUALIFY.

Expressions: Pratt parsing in parse_subexpr

Every expression goes through parse_expr, which is parse_subexpr(prec_unknown()), a floor of 0. parse_subexpr(precedence) is the whole Pratt loop:

pub fn parse_subexpr(&mut self, precedence: u8) -> Result<Expr, ParserError> {
    let _guard = self.recursion_counter.try_decrease()?;
    let mut expr = self.parse_prefix()?;              // an operand: a, 1, f(x), (…), CASE …, NOT x
    expr = self.parse_compound_expr(expr, vec![])?;   // a.b.c, a[1]
    loop {
        let next_precedence = self.get_next_precedence()?;
        if precedence >= next_precedence { break; }   // the next operator belongs to a caller
        expr = self.parse_infix(expr, next_precedence)?;  // consumes it, parses the right side
    }
    Ok(expr)
}

parse_prefix handles everything that can start an expression. parse_infix consumes an operator and, for a binary one, builds Expr::BinaryOp { left, op, right: parse_subexpr(precedence) } (L4178). The right side is parsed with the operator's own precedence as its floor, so an equal-precedence operator stops it: that is what makes a - b - c left-associative. get_next_precedence delegates to the dialect's get_next_precedence_default, a large match on the next token that also handles multi-token operators (NOT IN, IS, AT TIME ZONE) by peeking further.

How dialects bend expression parsing

Three hooks let a dialect change expression parsing without forking the parser: parse_prefix (take over parsing an operand), parse_infix (take over an operator) and get_next_precedence (change what an operator's precedence is). Each returns Option; None means "use the default". prec_value lets a dialect renumber the whole table. T-SQL overrides get_next_precedence only to give : the lowest precedence, so a colon is never read as a binary operator (mssql.rs L197). Most dialect differences are not hooks at all but boolean supports_* checks scattered through the parser.

3.5Options, errors and recursion limits

  • ParserOptions has three fields: trailing_commas (accept a, b, in every list), unescape (turn 'it''s' into it's; formatters want this off or use the token text), and require_semicolon_stmt_delimiter (default true; T-SQL scripts rarely use semicolons, so tsqlfmt turns it off). The last was added by #1937, deliberately as an option rather than a dialect hook.
  • Errors are ParserError: TokenizerError(String), ParserError(String) or RecursionLimitExceeded. The message carries the location of the offending token. There is no error recovery: the first error ends the parse of the whole input. tsqlfmt limits the blast radius by parsing one batch at a time.
  • Recursion: every parse_statement, parse_query and parse_subexpr takes a guard from a RecursionCounter, default depth 50 (L196). The guard gives the depth back when it is dropped, at the end of the function. With the default recursive-protection feature, deep functions are also wrapped by the recursive crate, which grows the stack on demand. maybe_parse deliberately does not swallow RecursionLimitExceeded.

3.6The AST type hierarchy

The top of the tree is enum Statement, with a variant per statement kind (about 150). A SELECT statement is Statement::Query(Box<Query>). From there the types follow the SQL standard's layering: a query is a body plus trailing clauses, a body is a set operation over simpler bodies, and the simplest body is one SELECT … FROM … WHERE … block.

DDL lives in ddl.rs (CreateTable, ColumnDef, ColumnOption, AlterTableOperation, CreateIndex), table constraints in table_constraints.rs, and data types in data_type.rs. Two conventions matter when you add to them. Large statement payloads are separate structs wrapped by a tuple variant (Statement::CreateTable(CreateTable)), so they can grow fields without touching the enum. And the derives are uniform: every AST type derives Debug, Clone, PartialEq, PartialOrd, Eq, Ord, Hash and, behind features, Serialize and Visit.

3.7Spans: Spanned and AttachedToken

Tokens have exact spans. AST nodes do not store a span of their own. Instead trait Spanned computes one on demand, "by recursively combining the spans of its children". The helper is union_spans, and the rule inside Span::union is that an empty span is ignored, so a child with no location does not poison its parent.

// spans.rs: a binary operation spans from its left operand to its right operand
Expr::BinaryOp { left, op: _, right } => left.span().union(&right.span()),
// a Select starts at its SELECT keyword, then takes in every clause it has
union_spans(core::iter::once(select_token.0.span)
    .chain(projection.iter().map(|item| item.span()))
    .chain(from.iter().map(|item| item.span()))
    .chain(selection.iter().map(|item| item.span())) …)

Sources: L1692, impl Spanned for Select.

Why unions? The design came from PR #1435 (merged November 2024). Earlier attempts wrapped every node in a WithSpan<T>, which would have broken every downstream user that builds or matches AST values. Computing spans from children adds no fields to most nodes, so the change was nearly invisible to users. The cost is that anything which is not a child, a keyword or a parenthesis, is invisible to the union. a IS NULL spans only a, because IS NULL is not a node.

The fix for keywords is AttachedToken. It wraps a TokenWithSpan and is stored in a node purely so the node can include that token in its span: Select::select_token, Insert::insert_token, CaseStatement::end_token, and about 40 more. Its trait implementations are rigged so that all attached tokens are equal (PartialEq returns true, Hash does nothing). That keeps AST equality semantic: select 5 and SELECT 5 parse to equal trees, and the thousands of assert_eq!(ast, expected) tests keep working. The flip side: no equality-based test can ever notice a wrong or missing attached token. Only tests that look at spans directly can. The generic wrapper Parens<T> holds an opening and closing paren token around a value, and derefs to the value.

Spans are incomplete upstream, by the project's own account. The trait's doc comment says spans "may be missing keywords or other tokens" or be missing entirely (spans.rs L61), and the README section is titled "Source Locations (Work in Progress)" (README). At 2ff068b3, about 101 Statement variants return Span::empty(). The tracking issue is #1548, "[EPIC] Complete Span (source location) information", open since November 2024. Its stated rules: prefer Span::union over storing spans, store keyword tokens as AttachedToken, never let span metadata change Eq, Ord or Hash, and proceed incrementally.

3.8Comments

Comments never enter the AST. Since #2107 (December 2025) and #2354, Parser::into_comments walks the retained token vector and returns a Comments table: a sorted list of CommentWithSpan, each with the comment's span and the end of the previous non-trivia token and start of the next. You query it by location with find(range) or find_before(location). Deciding which node a comment belongs to is left to the caller, deliberately. The design discussion is #2065: adding comment fields to nodes was proposed and rejected, partly because in select a /* one */ , /* two */ b the comma, which is not a node, is what the comments sit next to. This is the same side-table model as Go's ast.CommentMap.

3.9The visitor

With the visitor feature, every AST type implements Visit and VisitMut, generated by sqlparser_derive. The generated visit walks each field in declaration order. Types tagged #[visit(with = "…")] call the matching hooks on your Visitor: pre_visit_statement, pre_visit_query, pre_visit_select, pre_visit_expr, pre_visit_relation, and their post_ twins. Each returns ControlFlow, so a visitor can stop early. For one-off walks there are closures: visit_expressions, visit_relations, visit_statements.

struct PrintExprSpans;

    type Break = ();

3.12How to add a feature

Upstream's expectations are written down in three places: the README's "New Syntax" section, the dialect_of! doc comment and AGENTS.md. Put together, the recipe is:

  1. Find the documented grammar for every dialect that has the construct, not only the one you need. If it is standard SQL, it probably belongs in GenericDialect and AnsiDialect too. The README: "Any SQL feature that is dialect specific should be parsed by both the relevant Dialect as well as GenericDialect."
  2. Look for an existing AST node that already models the concept under another dialect's spelling (generated columns, optimizer hints, constraint validation). Extend it rather than add a parallel one.
  3. Add a dialect hook: a fn supports_x(&self) -> bool { false } on Dialect with a doc comment and an example, overridden to true in each dialect that has the syntax. Do not branch on dialect_of!.
  4. Add the AST node or field, with the standard derives, a doc comment linking the vendor's grammar page, and AttachedToken fields for any keyword or punctuation that starts or ends it.
  5. Write the parse function and call it from the right dispatch point, guarded by the hook.
  6. Implement Display so the output re-parses to the same tree.
  7. Implement Spanned as a union of the children and attached tokens.
  8. Test: verified_stmt for round trips, all_dialects_where(|d| d.supports_x()) for the positive cases and all_dialects_where(|d| !d.supports_x()) with an expected error for the negative ones. Put the test in sqlparser_common.rs when it is hook-gated.

4How tsqlfmt uses the parser

tsqlfmt is a T-SQL formatter at ~/code/personal/tsqlfmt. Its style baseline is JetBrains DataGrip's SQL style (STYLE.md), and its one hard rule is that only whitespace and letter case change: no token is added, removed or moved. It depends on the fork through a path dependency with the visitor feature. Paths and line numbers below refer to the working copy as reviewed and may drift. 4.1The pipeline

  1. Batches on GO. GO is not T-SQL; it is a client command that tells tools like sqlcmd where to cut the script (Microsoft Learn). sqlparser-rs has no notion of it (#1809 tried and went stale). tsqlfmt splits by line in format() (src/format.rs:34, loop at 65–77): a small hand-written lexer state, LexState (src/lib.rs:58), tracks whether the line starts inside a block comment, string or bracketed identifier, and a line is a separator only at top level and when is_go_line matches (GO, optional count, optional ; or comment). SQLCMD : lines are passed through the same way.
  2. Parse per batch. format_text (format.rs:209) tokenizes with Tokenizer::new(&MsSqlDialect {}, text).tokenize_with_location(), then hands the same vector to Parser::new(&MsSqlDialect {}).with_options(…).with_tokens_with_locations(toks).parse_statements(), with require_semicolon_stmt_delimiter: false. One bad batch does not stop the others; the file-level test unparsable_batch_is_verbatim_others_formatted pins this.
  3. Tokens and trivia. layout_from_tokens (format.rs:239) splits the stream into Toks (non-trivia tokens, with their source text sliced from the input) and, for each gap between them, a Trivia list of newline counts and comments. Spaces only set a flag. Gap i is the whitespace before token i, and every gap starts as Rule::Src: keep the source line break, re-indented relative to an anchor token.
  4. AST to rules. build::build walks the statements top-down. Each handler maps its node to a token range through the node's span, resets the gaps inside that range to Src, recurses into its children, and then sets the gaps between and before them (next section).
  5. Print, one left-to-right pass that only writes whitespace between token texts (4.3).
  6. Verify, then keep or discard (4.4).

4.2Mapping nodes to tokens through spans

The core function is small. Given a node's span, find the first token that starts at or after the span's start and the last token that ends at or before its end, by binary search over the trivia-free token list:

// tsqlfmt src/build/mod.rs, Builder::range
pub fn range(&self, span: Span) -> Option<R> {
    if span.start.line == 0 || span.end.line == 0 { return None; }   // empty span: no mapping
    let toks = &self.l.toks;
    let a = toks.partition_point(|t| loc_lt(t.start, span.start));
    let b = toks.partition_point(|t| !loc_lt(span.end, t.end));
    if a >= toks.len() || b == 0 || b - 1 < a { return None; }
    let a = self.extend.get(&span.start).copied().unwrap_or(a);    // patch table for missing keywords
    Some((a, b - 1))
}

Ownership follows from the walk order rather than from an explicit token-to-node table: a handler owns the gaps strictly inside its range, the innermost handler sets a gap last, and a parent only overwrites the gaps at its children's boundaries. Two escape hatches handle what spans cannot. The extend table moves a range's start back onto a keyword that the AST leaves out (USE, VALUES, TRUNCATE TABLE, a statement's leading keywords). And when range returns None (an empty span), the handler falls back to generic, which formats the nearest nested Expr, Query or Statement nodes and leaves the node's own gaps as Src. Attached tokens are used directly where the AST has them: Builder::att finds the token that starts at an AttachedToken's location (begin_token, end_token, window parentheses).

4.3Gap rules and the printer

A gap's Rule (src/layout.rs:141) says whether it may break and how much space it gets: Src (keep the source break, re-indented), Flat(sp), Break(indent), BreakIf(group, …) (break if the group breaks), Keep (break if the source did), FlatIn, SpaceIf and Fill (break only if the next chunk does not fit). Indents are relative to previously printed tokens (Col, LineOf) rather than nesting levels. A Group is a token interval whose BreakIf gaps break together.

The printer (print, layout.rs:244) makes one left-to-right pass. When it reaches the first token of a group it decides once whether the group is broken (group_broken, layout.rs:697): yes if forced, if the group is a keep group and the author broke it in the source, if it contains a comment that forces a break, or if the group plus the flat text after it would pass column 120. Groups inside a flat group are flat. There is no backtracking and no cost model. Alignment of aliases and column types uses cells: each pass records columns, and print repeats up to four passes until the alignment targets stop moving.

Comments are never attached to nodes. They sit in the trivia of the gap they were found in, so their order relative to tokens cannot change. A -- comment forces a break after it, and a trailing comment keeps its distance from the token before it so columns of comments stay aligned (Printer::trivia, layout.rs:606). parse-time Comments from into_comments are not used by the formatter.

4.4The safety net

verify (format.rs:392) re-tokenizes the output and compares it with the input, ignoring spaces, tabs and newlines but not comments. Two words may differ only in ASCII case, and only at positions case::apply recorded as changed. Any other difference, or output that fails to tokenize, returns Mismatch, and the batch is emitted verbatim. The printer cannot drop or reorder tokens by construction, so this check guards against bugs in the case logic and in the layout's handling of trivia. It does not check that the layout is good; golden tests and an idempotency check (tests/golden.rs) do that.

Coverage. Two more subcommands measure the parser rather than the formatter. tsqlfmt check counts the files of a corpus whose batches all parse; tsqlfmt spans audits every AST node's span against the tokens and groups the findings. On the author's private corpus of 510 files, check went from 263 with upstream v0.64.0 to 414 after the first 20 fork changes, 478 with optional semicolons and GO handling, and 480 after the second batch (5.4). The 30 files that still fail are placeholder templates that are not valid SQL. spans reports 96 findings in 5 groups, all known before the second batch: the USE keyword outside its statement's span, the ) of table hints, and WITHIN GROUP (…). Both numbers measure one corpus. They say nothing about constructs the corpus does not contain, which is why the fork review below judges changes against the documented grammar instead.

4.6AST spans over tokens, or a lossless tree?

What the span-over-tokens design buys

  • The grammar comes for free: a large, actively maintained T-SQL parser, upgraded by rebasing.
  • A strong, cheap invariant. Because the printer only writes whitespace between the original tokens, comments cannot be lost or reordered, and verification is a token comparison.
  • Graceful degradation. An unknown node or empty span leaves the source layout (Src) instead of failing.
  • Small code: the formatter is a set of handlers over upstream types.

What it costs

  • Formatting quality is bounded by span completeness. Every hole is either a gap left at Src, an entry in the extend patch table, or a fork change to the parser. The 19 span changes (S1–S19) exist for this reason.
  • Spans give extents, not ownership. Commas, parentheses and keywords are found by peeking at token kinds next to child ranges.
  • Span regressions are invisible to the parser's own tests, because AttachedToken always compares equal.
  • No error recovery: one unsupported construct leaves its whole batch verbatim. Lossless parsers such as rowan-based ones recover and still format the rest.
  • Line and column locations, not offsets, so every lookup converts.

Assessment. For a formatter whose contract is "whitespace only", building on tokens is the right call; clang-format and JetBrains prove the model. The weak part is the bridge from AST to tokens. Upstream has twice declined to become lossless: #189 prototyped a rowan-style tree in 2020 and was closed, and #2077 (removing whitespace tokens) was rejected in 2025 partly because formatter and linter users need those tokens. Writing a separate lossless T-SQL parser would cost far more than the formatter itself. So the realistic choices are: keep spans, but make span completeness a deliberate, upstream-shaped project with a test oracle (as proposed in #2567), or record node extents as token indices in one central place in the parser, which would give tsqlfmt exact ranges with no per-node fields. The fork currently does neither; it patches node by node. Section 5.3 reviews those patches.

5.3Span changes (S1–S18)

All eighteen (and S19 in the second batch) exist so that tsqlfmt's range() finds the right tokens. They use upstream's mechanism, AttachedToken fields unioned into the node's span, and mostly upstream's field names. The questions are whether they agree with the design in #1548 and whether upstream could take them. Two new tools recur:

  • Parser::last_consumed_token (added in S1): the last non-whitespace token before the cursor, used to fill end_token fields. It is needed because get_current_token can point at whitespace after prev_token. But "whatever was consumed last" depends on how much a sub-parser happened to swallow, not on the grammar. Upstream's only end-of-statement token, AlterTable::end_token (#1999), deliberately includes the ;; the fork's policy is to exclude it, and it changes AlterTable to match (S8). The policy is not enforced: probe shows CREATE TRIGGER trg ON t AFTER INSERT AS SET NOCOUNT ON; SELECT 1; spans to column 66, past the final ;.
  • Post-hoc patching: with_create_token and with_alter_token take a statement that a sub-parser returned with empty tokens and fill in the CREATE / ALTER keyword and the last token afterwards. The fork's parser has 54 AttachedToken::empty() placeholders against one upstream (58 after the second batch). The closed upstream PR #2571 recorded first and last tokens centrally instead, skipping ; and EOF.

Size. An AttachedToken is 88 bytes (a full Token plus a span) and cloning a word token allocates its string. A first-and-last pair costs 176 bytes to record what two 32-byte spans would. Measured upstream → fork: Expr 328 → 272 bytes (boxing in S4 and S14 more than pays for the new tokens), Statement 3,464 → 3,640, Query 1,408 → 1,616, ColumnDef 144 → 232.

Coverage after the series. Span::empty() occurrences in spans.rs go from 194 to 176 (170 after the second batch); Statement arms returning empty from 101 to 82. Probe shows holes the series leaves: EXTRACT(YEAR FROM d) and CEIL(x) span only their operand, and … FROM t WITH (NOLOCK) gives both the table and the Select a span that stops before the closing ).
